# Particle runtime benchmark fixtures

Run `cargo bench -p wc3 --bench particle_runtime` from the repository root. These four original baked 2.5.1 PKB files contain no acquired game bytes or reference implementation code. Regenerate them with `python3 crates/wc3/benches/fixtures/particle_runtime/generate.py`, or add `--check` to verify deterministic bytes without rewriting anything. The generator requires only Python's standard library. Its adjacent manifest records the shared native instruction/field contract once, plus each variant's burst count, byte length and SHA256. The two root programmes' one variable constant is explicitly marked `f32(burst_count)`; generation verifies that no other contract data differs. Native parsing, checked compilation and public runtime assertions remain separate validation performed by the benchmark when run.

Each fixture has one persistent renderer-free controller and exactly 1, 8, 128 or 1024 persistent renderer children. The first tick generates the requested burst; later ticks execute the real generate/initPayload/kick calls with zero new children. Every child runs 23 native evolution instructions: typed field loads, scalar arithmetic, an interpolating Float4 Hermite curve sample, vector multiplication and six renderer-field stores. The children have zero inverse lifetime and do not die or respawn. A native material resource name is retained; this core-only workload neither loads images nor renders.

The separately named preparation cases measure native compilation of an already decoded document and empty runtime instantiation, including destruction of the returned object. Instantiation does not start or initialize its controller. The steady cases measure 64 positive ticks across one or eight instances, using capacities 128 or 1024 renderer children plus their controller. Small populations exercise the default runtime at scalar-sized workloads. Dense populations provide contiguous same-layer surviving children and a pure instruction body designed to fit the generic packet subset. Public canonical outputs cannot establish which private backend executed: the benchmark makes no internal dispatch assertion, exposes no backend switch and should not be used as a packet-coverage probe.

Before Criterion calibration or timing, a separate original oracle examines every child at every one of the 64 measured timestamps plus the warmed initial state. It verifies all 14 canonical fields (including all six renderer inputs), checked value types and inactive words, every parent link and unique birth serial, lifetime invariance and exact layer populations. Constants and zero pass-throughs are checked bitwise. Dynamic fields are compared against the authored scalar formula and an independent f64 closed cubic for the curve's first segment, with a bounded f32 rounding allowance. Renderer bindings and the source field order are checked through public compiled descriptors. This is an observable-output proof, not access to private VM scratch or packet plans.

Every measured batch is newly instantiated, started and warmed for two 1/64-second ticks in Criterion's untimed `PerIteration` setup. Its timed block advances exactly 64 ticks. Effect time therefore stays between 2/64 and 66/64 seconds, so the authored `scene.time/16` input remains strictly inside its first `(0,1)` interpolating segment. Long Criterion runs repeat the same bounded trajectory rather than drifting into constant endpoint sampling. Each iteration retains only its current batch; setup can extend wall-clock duration but is excluded from the steady measurement.

Stable active count, total initialized count, zero retirements and every omission/suppression counter are asserted at the warmed and final batch boundaries. Final O(1) population/stat/time assertions and the nested iteration boundary are **included** in the steady measurement, named `warmed_64_ticks_with_validation`. The full per-particle oracle is outside that measurement and outside every timed iteration. Throughput counts active-particle ticks, including the controller. Allocation, start and warmup are outside the steady timing.

These maintained benchmarks support reproducible local regression investigation. They do not replace exact trajectory/counter admission, private dispatch-coverage probes, immutable matched paired runs or the separate small/dense performance gates. They establish no cross-engine speed claim.
