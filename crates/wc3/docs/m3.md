# M3 model documents

M3 stores arrays in indexed sections. Each section names its own record revision,
and references connect records through section indices and entry counts. The
`wc3::model::formats::m3` API keeps that graph intact, including shared targets, reference
flags, section order, and independently selected revisions. It reads and writes
native model and external animation documents. Semantic adapters live under
`wc3::model::io::m3`; rendering remains separate from file access.

## Choosing an envelope and inspecting records

Choose `Model<Md33>` for the older eight-byte reference envelope or `Model<Md34>`
for the twelve-byte reference envelope. `DynamicDocument::read` detects the envelope
from the native signature when the caller does not know it. Neither choice sets
a file-wide record revision: the index entries determine each section's layout.
For a new file, `Model::<Md34>::new::<StarCraft2>()` chooses MODL revision 29;
`HeroesOfTheStorm` chooses revision 30, and `Model::<Md33>::new::<Beta>()`
chooses revision 23. These creation defaults do not convert existing records.

`Model::document()` exposes the checked graph. Each `Section` reports its tag,
revision, entry count, and native bytes. `Model::root::<T>()` selects an exact
MODL revision, while `root_record()` dispatches to an enum retaining the native
revision and offers common metadata accessors. `Container::array::<T>(id)` and
`Container::resolve(reference)` open borrowed arrays through exact record types. A revision mismatch returns an error
instead of upgrading the source representation. Family references can be
inspected with `referenced_section` before selecting a concrete record revision.

The `records` modules separate animation, geometry, materials, effects, physics,
and scene metadata. Each revised family uses a single generic record, such as
`ModelRecord<V23>`, `TextureLayer<V22>`, or `Region<V5>`. Family dialect traits
select associated field types: an absent field uses `()`, a present field uses
its native scalar or reference type, and a width change selects the appropriate
integer or array type. Revision markers are independent choices for each section.
Families with one supported revision need no revision parameter. The record
structs derive `m3::Read`, `m3::Write`, `m3::RecordLayout`, `m3::Validate`, and `m3::VisitReferences`.
`SUPPORTED_RECORDS` and `known_layouts` expose the supported tag-and-revision
matrix. Unknown tags and unsupported revisions remain encoded payloads; their
bytes are preserved without claiming to interpret their fields.

Choice fields use named enums with `Unknown(wire)` variants that preserve
unrecognized codes. Flag fields use `bitfield!` types with named getters and
setters; `bits()` retains the complete stored word. `m3::Value` generates
exact code conversions for custom scalar enums alongside the codec derives.
Revision numbers, indices, and counts keep their numerical types.

Record fields keep their native meaning when two layouts happen to share a
size. `Bone<V1>` begins with a signed identifier before its name reference;
`Bone<V0>` exposes the leading legacy word as an unsigned value through the
same `id` dialect field. `Bone::batching` animates the draw batches that
reference the bone. `ShadowBox` contains a bone index, padding, and animated
length, width, and height controls. The bone `batching` property carries native
draw-batch flags rather than a generic visibility value. A rigid body's `mass` stores authored mass,
and `gravity_factor` scales gravity. The
[m3studio structure schema](https://github.com/Solstice245/m3studio/blob/main/structures.xml) documents native field layouts.

`texture_dependencies()` inspects native material path fields and returns borrowed filename bytes with declaring field identities;
`Container::string` reads null-terminated UTF-8 arrays when text access is wanted.

## Editing a shared graph

A `SectionId` belongs to its document. Cloning or borrowing a document keeps its
identities, while IDs from an unrelated document are rejected. Appending arrays
retains existing indices, so an edit does not duplicate shared targets. A native
`Ref<T>` carries the number of requested entries, the section index, and the
MD34 flag word. Empty references retain their encoded metadata and do not resolve
a target.

Move a model into its document to edit it. `append` adds typed record arrays,
`replace` replaces records of the same native revision, and `replace_bytes`
replaces encoded payload bytes. Set the header reference with `set_root`, then
use `Model::from_document` to validate the result. A model requires exactly one
supported MODL root. Validation checks understood record spans and target tags,
indices, and entry counts without recursively loading target arrays, so sharing
and graph cycles do not require eager decoding.

`clear` empties an unreferenced section while retaining its table slot. It rejects
removal of the header, model root, referenced records, or records whose incoming
references cannot be established because an opaque section exists. Explicit
record conversion can be added separately without weakening native revision
checks.

## Storage and writing

Section payloads and fixed-record arrays borrow the original file. Reading an
array element decodes that record on demand. Editing an array or replacing a
section allocates owned bytes for that storage. `as_borrowed` creates a view of
owned or borrowed buffers, and `into_owned` detaches the source for long-lived
use. Standard I/O adapters buffer a stream, validate it, and return owned models.

Writing an unchanged source preserves it byte for byte. When every section is
understood, the writer relocates payloads, restores native alignment, and rebuilds
the index table while retaining section identities and revisions. Native MD34
flags are retained; writing nonzero flags through MD33 fails because that
reference envelope has no flag word.

An opaque payload may contain pointers absent from its known schema. Such files
therefore require their original placement: edits must preserve section lengths
and table slots. Appending or resizing returns an error. This preserves unknown
bytes without treating arbitrary relocation as safe.

## Packed geometry and external animations

Packed geometry views retain native position, direction, color, weight, index,
and texture-coordinate bytes. Layout markers select field interpretation, and
storage capabilities determine whether setters are available. A single
`Vertices<Storage, Layout, Shape>` represents owned or borrowed buffers and
individual mutable or immutable views. `Packed<UV_MASK, Color, Extra>` selects
sparse UV channels, color storage, and an optional uninterpreted slot. The
`One` and `Many` shape markers distinguish individual fields from array access,
and UV and color accessors require those fields in the layout type. Unsupported
or ambiguous packed layouts remain available as raw bytes rather than receiving an
assumed interpretation.

External `.m3a` files use the same indexed document machinery. Bundle APIs keep
external animation documents separate and match them through their native
animation hashes. Each document retains its own envelope and section revisions;
writing a bundle produces coordinated model and animation bytes without merging
or converting their graphs. Nonzero authored binding hashes must match the
resolver identity. An absent authored hash requires an explicit caller-supplied
association; the API does not invent filenames or the toolchain's hash algorithm.

Semantic conversion imports the complete bundle into editable clips. Export rebuilds
these tracks inside the model, clears companion dependency hashes, and reports
this change in animation storage. Native bundle access remains available when
separate animation documents must retain their original layout. The conversion
adapter also retains unreferenced shader rows as editable native materials,
including anisotropic hair surfaces.

The format includes unresolved fields and deprecated record revisions. Those
fields retain their native values, and raw access remains available where their
meaning is not established. Structural validation establishes safe native access;
it does not establish rendering fidelity or evaluate animation playback.
