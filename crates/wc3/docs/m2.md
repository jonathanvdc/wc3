# Reading and editing M2 models

World of Warcraft's M2 models live under `wc3::model::formats::m2`. A model has a typed
core layout and a separately selected file envelope, while supporting documents
retain their own native representations. This guide explains how to edit an
individual document and how to connect the files needed to interpret external
animation data. Warcraft III MDX and MDL use the separate
[`wc3::model::formats::mdlx` APIs](models.md).

The M2 codec APIs cover file formats and their references.
[Semantic import and export adapters](conversion.md) live under
`wc3::model::io::m2`. The [Bevy renderer](../../bevy-wc3/docs/rendering/renderer.md)
consumes imported semantic models with separately documented material and effect
coverage.

## Choose a layout and envelope

Use `Document<Flat<V274>>` for a version-274 flat MD20 file, or
`Document<Chunked<V274>>` for a chunk stream containing an MD21 core. The same
choice is available for every supported marker. A typed decoder checks both the
numeric version and the envelope; `DynamicDocument::decode_m2` detects them from
input bytes when they are not known in advance. Unknown numeric versions are
rejected rather than assigned the nearest known layout.

The header version identifies a record layout rather than a client expansion.
In particular, version 272 appears across multiple client generations and can
use either envelope. Its sequence blend-time word also has two interpretations:
`V272PreSplit` retains one `u32` for earlier files, while `V272` uses the later
incoming/outgoing `u16` pair. Numeric-version detection selects the latter.
Choose the earlier interpretation with the typed marker or
`DynamicDocument::decode_m2_with_layout::<V272PreSplit>(bytes)` when the producing
client requires it; neither API infers client provenance from the file. The
following distinctions determine which native fields are present:

| Layout | Native representation |
| --- | --- |
| `V256` | Float bone quaternions, flat animation timelines with interpolation ranges, sequence start/end timestamps, embedded skin profiles, legacy particle lifetime blocks, an uninterpreted classic lookup array, and a preserved 16-byte header tail. |
| `V257` | The classic representation with an additional header array descriptor and eight preserved trailing header bytes. The extra array's element layout is unknown. |
| `V260` | Compressed bone quaternions, flat timelines, texture flipbook tracks, and embedded skins; skin sections include their sorting center and radius. Particle blending and emitter types retain their wide fields. |
| `V263` | The late-TBC numeric layout, with packed particle blending/emitter fields and their color index, alongside the legacy timelines, flipbooks, and embedded skins. |
| `V264` | Per-sequence animation arrays, sequence durations, external skin profiles, external animation streams, and revised effects records. Cameras retain a scalar field of view. |
| `V265` | Animated camera field of view, shadow skin batches, and revised particle fields. |
| `V272PreSplit` | Version 272 with a single sequence blend-time word and modern camera and particle records. |
| `V272` | Version 272 with separate incoming/outgoing sequence blend times and extended particle scrolling fields. Versions 264–271 can also select extended particle fields through a core flag. |
| `V273`, `V274` | Their exact numeric identities, with the established modern core records and independently decoded extension chunks. |

Layout markers also select record types: for example, `Bone<V256>` has float
quaternion tracks, while `Bone<V264>` has compressed tracks. Runtime flags and
external animation references remain values within those layouts.

`Flat<V>` and `Chunked<V>` select framing without converting any records.
`into_chunked()` wraps a flat core in an MD21 chunk; `into_flat()` rejects a
chunked document that contains additional chunks, since those cannot be written
in a flat envelope. Allowing both envelopes for a marker does not establish that
a historical game exporter used every combination.

## Edit native records and borrowed arrays

`model.core()` and `core_mut()` expose the core's collections and fields. The
`records` module defines geometry, materials, sequences, bones, attachments,
events, lights, cameras, ribbons, particles, and animation headers. Historical
fields retain their native representations: legacy sequence timelines are not
silently rebased, float quaternions are not compressed during parsing, and
spline values retain their incoming and outgoing tangents.

Encoded fixed-width arrays use `ZeroVec`, including model vertices and
materials. Offset-bearing records use Rust collections whose nested leaf arrays
borrow their encoded source. Reading an unaligned little-endian array does not
require copying it into an aligned native buffer; `get()` and `iter()` return
ordinary Rust values. `IntoZeroVec` accepts native arrays, vectors, and slices
when replacing a field:

```rust
use wc3::model::formats::m2::{Chunked, IntoZeroVec, Document, V274};

fn rename(source: &[u8]) -> Result<Vec<u8>, Box<dyn std::error::Error>> {
    let mut model = Document::<Chunked<V274>>::decode_m2(source)?;
    model.core_mut().name = b"Renamed\0".as_slice().into_zero_vec();
    model.validate()?;
    Ok(model.encode_m2()?)
}
```

Keep input buffers alive while their documents borrow them. `as_borrowed()`
creates a view that borrows the original's buffers; `into_owned()` copies
borrowed storage and moves owned buffers into an independent document. An
existing `ZeroVec` retains its buffer when passed through `IntoZeroVec`. Editing
an array's encoded elements copies only that borrowed array into owned storage.

`decode_m2()` checks framing, record widths, and local count/offset bounds.
`validate()` additionally checks available cross-record relationships, including
animation aliases and bone parent topology. Whole-document encoding assigns
fresh offsets to understood local arrays. Use `m2::Read` and `m2::Write` in
format-qualified generic bounds. Their composable `read` and `write` methods
operate in a `codec::Decoder` or `codec::Encoder` address space; whole-model
entry points remain `decode_m2` and `encode_m2`. `m2::from_reader`,
`from_reader_dynamic`, and `to_writer` adapt standard I/O. Reader adapters buffer and detach their results,
and the writer adapter encodes before writing without flushing its sink.

For custom records, the `m2::Read`, `m2::Write`, `m2::RecordLayout`,
`m2::Validate`, and `m2::VisitArrays` derives handle field traversal. Contextual
animation data and cross-field validation still need handwritten logic. See the
[derive guide](../../wc3-derive/README.md) for details.

A dynamically detected model retains its concrete typed variant. Match that
variant for version-specific fields, or use `m2::visit_m2_model!` to apply an
operation that works for every supported layout:

```rust
use wc3::model::formats::m2::{self, DynamicDocument, IntoZeroVec};

fn rename_dynamic(source: &[u8]) -> Result<Vec<u8>, Box<dyn std::error::Error>> {
    let mut model = DynamicDocument::decode_m2(source)?;
    m2::visit_m2_model!(&mut model, |typed| {
        typed.core_mut().name = b"Renamed\0".as_slice().into_zero_vec();
    });
    Ok(model.encode_m2()?)
}
```

## Supporting documents and animation context

A modern M2 model can refer to several kinds of supporting files. Their public
modules provide standalone codecs, so applications can inspect or edit a file
without assembling a model bundle:

| Module | Document and data |
| --- | --- |
| `m2::skin` | `File` and `Profile`: vertex indirection, triangle indices, bone remapping, skin sections, rendering batches, and later shadow batches. Pre-264 profiles instead appear directly in the typed core’s `skins` vector; later cores store an external profile count. |
| `m2::geometry` | `File`, `Chunk`, and `VertexStream`: modern format-coded geometry streams, with preserved structural and collision payloads. |
| `m2::animation` | `File`: raw external animation bytes or ordered chunk streams such as AFM2, AFSA, and AFSB. |
| `m2::skeleton` | `File` and `Chunk`: skeleton headers, attachment and bone tables, sequences, lookups, parent skeleton references, and animation/bone file IDs. |
| `m2::bone` | `File`: version-1 sparse bone indices and their authored transform matrices. |
| `m2::physics` | `File` and `Chunk`: PHYS versions 0–6, body and shape layouts, capsules, spheres, boxes, polytope topology, joints, vegetation tuning, and host-skeleton allow lists. The same codec reads inline PFDC physics. |

Companion types are also available through `m2::companions`, under their
descriptive names such as `Skin`, `Skeleton`, and `PhysicsFile`. Standalone skin
and skeleton types select the owning model's layout through their type
parameter, for example `skin::File<V274>` and `skeleton::File<V274>`. Skeleton
records also depend on the owner's runtime flags. Neither codec infers a layout
from the companion filename.

Modern geometry documents can occupy references otherwise used for skin
profiles. `geometry::File` retains an ordered chunk stream; `VertexStream`
uses `StreamValues` to expose `1U16`, `2F32`, `3F32`, and `4U8N` packed elements
as borrowed `ZeroVec` arrays. An unknown format retains its literal format code
and payload without assuming an element width. Container-version, geometry,
batch, LOD, stream-descriptor, and embedded-skin chunks have named opaque
representations because their payload layouts remain unverified. Collision
chunks likewise retain their bytes without assuming a vertex-stream prefix.

An external animation file carries keys whose descriptors live in a model or
skeleton. `animation::File::read(bytes, chunked)` therefore requires explicit
framing context. Raw animation bytes have no reliable magic, and interpreting a
known FourCC at their beginning as framing would be ambiguous.
`codec::Array::External` retains an unresolved count/offset descriptor until an
explicit stream is supplied. AFM2 carries model animation data; split skeleton
files use AFSB for bones and AFSA for attachments. Global-sequence keys remain
separate from ordinary per-sequence streams.

A skeleton can inherit its sequence definitions from a parent. Use
`skeleton::File::read_with_sequences` to supply inherited external-sequence
flags; an SKS1 chunk in that file supplies its own flags and takes precedence.
Without either context, a standalone skeleton preserves unresolved ordinary
sequence leaves rather than assuming that their offsets point into the
skeleton itself. For a version-272 skeleton from the earlier blend-time profile,
select `skeleton::File<V272PreSplit>`. A bundle carries each owning model's selected
layout into skeleton decoding and writing, including referenced models whose
layout differs from the root.

## Resolve and encode a bundle

`dependencies(owner)` reports declared supporting files without accessing the
filesystem or an archive. Each `Dependency` retains its `owner`, `key`, and
`kind`. `FileKey` represents UTF-8 paths, arbitrary native path bytes, game file
IDs, a caller's root identity, or logical sibling names. Filename spelling and
separators are preserved; a resolver decides how relative names and file IDs map
to its storage.

Modern file-ID chunks take precedence over their corresponding filenames.
Legacy base-skin and animation names derive from the root filename, while skin
IDs distinguish base views from additional LOD views. Optional legacy LOD skins
and numbered bone siblings have no dependable declared count, so an application
must discover and attach them explicitly if it needs those files. Replaceable
textures are game-provided resources rather than literal external filenames.

`Bundle::decode` follows declared model and skeleton references through a
caller-owned resolver. Every declared nontexture document must be supplied;
texture bytes are not required to interpret model records. A skin dependency
whose source starts with `SKIN` uses the standalone skin codec; other sources
use the modern geometry codec. Returned byte slices
must remain alive because the bundle borrows them. For example, an application
can prepare its source buffers in a map before decoding:

```rust
use std::collections::BTreeMap;
use wc3::model::formats::m2::{Bundle, Chunked, EncodedBundle, FileKey, V274};

fn rewrite(
    source: &[u8],
    key: FileKey,
    sources: &BTreeMap<FileKey, Vec<u8>>,
) -> Result<EncodedBundle, Box<dyn std::error::Error>> {
    let bundle = Bundle::<Chunked<V274>>::decode(source, key, |dependency| {
        Ok(sources.get(&dependency.key).map(Vec::as_slice))
    })?;
    bundle.encode().map_err(Into::into)
}
```

For staged assembly, start with `Bundle::from_model(model).with_key(key)` and
`insert` native documents using the bundle's `File` enum. Typed skin and
skeleton documents convert into `File` with `into()`. `file_mut()` allows edits
to a supporting document. The `File::Skin` and `File::Skeleton` variants retain
`DynamicSkin` and `DynamicSkeleton` wrappers, since a referenced model can use
a different layout from the root. Use `as_typed::<V>()` or
`as_typed_mut::<V>()` to access a known native layout; these return `None` when
the marker differs. The `visit_m2_skin!` and `visit_m2_skeleton!` macros dispatch
operations that apply to every native variant.

`validate_complete()` checks required document kinds, owning layouts, parent
cycles, and external animation bounds. `profile(index, lod)`
returns a `ProfileRef` for an embedded profile, standalone skin, or modern
geometry document. Embedded profiles use `lod = false`; additional LOD views
are separate external dependencies. The narrower `skin(index, lod)` and
`geometry(index, lod)` accessors require their respective supporting-file
representations. `resolve_track()` and `bone_translation()` expose native keys
from their owning streams without evaluating an animation. For a batch of key
reads, borrow `bundle.animation_resolver()` and use its corresponding resolve
methods. The resolver retains dependency, owner-layout and sequence metadata for
that immutable bundle view; returned keys still borrow their native buffers.
After releasing the view and any borrowed keys, edit the bundle and create a
new resolver to observe those edits. Semantic import uses one such view while retaining
all native animation sequences.

A resolved track is a borrowed view. For per-sequence bone translation edits,
`set_bone_translation(sequence, bone, timestamps, values)` locates the native
owner and checks timestamp ordering, cardinality, and the spline representation
before replacing any keys. Supply `ResolvedValues::Values` or
`ResolvedValues::Splines` to match the existing track. Legacy flat timelines
require direct native track editing.

For other external key edits, replace the relevant timestamp and value leaves
in the owning record with `codec::Array::Inline` arrays containing the edited
values. Sequence flags determine whether those
arrays are emitted locally or into an external animation stream during bundle
encoding. Keep timestamp and value counts consistent, including spline triplets.

`Bundle::encode()` coordinates external animation arrays and updates their
owner's descriptors together. It returns `EncodedBundle { model, files }`, where
`files` is a map from existing `FileKey` identities to encoded supporting
documents. Writing paths, assigning archive IDs, and packaging those outputs
remain application decisions. Encoding an individual model relocates its local
data while leaving unresolved external descriptors intact; use bundle encoding
when changing keys that belong in supporting animation streams.

## Import for shared editing or rendering

Use `model::io::m2` to import a bundle into a checked graph. Generic callers can
bound their dialect by `io::m2::ImportDialect`, which covers the flat and chunked
forms of each supported native layout. The
[conversion guide](conversion.md) explains policies and export plans;
[materials](materials.md) and [features](features.md) describe its shader and
emitter definitions. Native documents remain useful for inactive lookup entries,
unresolved controls, and other records that have no graph interpretation.

M2 import groups consecutive skin batches with the same auxiliary section word
into one draw after ordering by native material layer. Export regenerates dense
layer numbers. Shader-selected UV and environment routes determine the active
texture inputs; repeated routes must retain compatible animation bindings for
exact export.

Each semantic M2 mesh also retains its section's declared bone palette as logical
node IDs, including unused members. This declaration differs from the full skin
binding: an explicit empty palette remains empty, while an absent declaration
permits inference for authored geometry. The NoBodySpawn bone control is retained
independently of billboarding. These relationships supply body-particle generator
eligibility without inspecting raw native records at runtime. Strict export
rejects a weighted skin joint outside an explicit palette because adding it would
change that eligibility; accepting unsupported loss permits and reports the
expansion. Native documents retain their original arrays independently of this
semantic export boundary.

Particle appearance uses normalized-age curves, separately from emitter animation.
Modern lifetime timestamps use fixed15 units, where `32767` marks the end of life.
Directional gravity is decoded before interpolation. Native head/tail selection
is retained, including disabled modern geometry, which legacy layouts cannot
represent. TXAC particle hints require full graph export into a chunked container;
standalone particle export cannot carry them. Nonzero material hints need an
explicit loss policy because they have no established surface interpretation.

These adapters preserve established meanings; they do not run particle simulation
or resolve external effects. The renderer's [sprite guide](../../bevy-wc3/docs/rendering/pre2.md)
describes its implemented subset and remaining fidelity limits.

## Coverage and preservation boundaries

The core and companion codecs implement the established record layouts listed
above. Modern model chunks are retained in their original order, including
unknown chunks and repeated tags. `validate()` requires a single core; additional
MD21 cores can be inspected and preserved by decoding but fail that consistency
check. The catalogue below covers the 30 documented M2 tags and distinguishes
typed payloads from data whose interpretation is not established:

| Tags | Current representation |
| --- | --- |
| MD21 | Typed core model address space. |
| PFID, SFID, AFID, BFID, SKID, TXID, RPID, GPID | Typed supporting-file IDs, including animation ID/variation records and ordered skin IDs. |
| TXAC | Encoded texture and particle combiner hint pairs. |
| EXPT, EXP2, PGD1 | Typed particle extensions, lifetime alpha-cutoff arrays, and particle geoset assignments. EXP2's additional offset-addressed bytes are preserved and relocated without assigning them undocumented semantics. |
| PABC, PADC, PSBC, PEDC | Offset-addressed parent animation blacklist, texture weights, sequence bounds, and event tracks. |
| LDV1 | Native LOD configuration fields, including its encoded scale and particle-bone masks. |
| WFV1, WFV2, WFV3 | Marker chunks and the known waterfall data fields. |
| PFDC | Typed PHYS document with regenerated inline alignment padding. |
| EDGF, NERF, DETL, DBOC, TEXL | Typed fade, opacity, and lighting records; encoded half-float fields retain their bits. |
| PCOL, DPIV | Offset-addressed collision geometry and native pivot displacement records. Some field meanings remain inferred. |
| AFRA | Preserved bytes; the animation frame-rate payload layout is unknown. |

Unknown chunks retain their exact payload bytes, but the codec cannot update
undocumented references inside those payloads. Known records preserve reserved
fields and unknown flag bits; output may change padding and local allocation
order, so semantic round trips do not promise identical complete files.

The classic-only `Core::classic_lookup` array and version 257's extra header
array have unknown element widths and potentially unknown internal references.
Their `OpaqueArray` or header-tail representations retain the complete original
core address space when an array is nonempty. Its storage stays at its existing
offsets, and understood arrays are written into newly appended storage. This
preserves unknown records without guessing their extent; output can consequently
be larger than a compact rebuild. These descriptors cannot be used to author
new unknown records without retaining that source address space.

The supporting geometry codec separately recognizes VPOS, VNML, VTAN, VWTS,
VIBP, VINX, VUV0–VUV5, and VCL0/VCL1 stream tags. Its four established format
codes are typed; unknown codes remain raw. M3VR, VGEO, RBAT, LODS, VSTR, and
SKIN structural payloads and CPOS, CNML, and CINX collision payloads are
preserved without interpretation. Resizing a stream or rearranging chunks can
invalidate undocumented references in those preserved payloads. Retaining their
bytes does not guarantee that such edits produce a compatible geometry document.

Structural format support does not establish compatibility with every historical
exporter or game build. Broad game-corpus compatibility remains unverified.
WoW Model3 remains a separate format outside the M2 codecs. Unknown tags in M2
and supporting geometry streams retain their payloads without an inferred layout.
